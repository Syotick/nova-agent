# 练习册 06：上下文压缩

> 读完 [指南 06](../guide/06-compact.md) + 代码 `server/compact.ts` 后完成。规则：先自己动手，做完再对答案（答案在 [answers/06-compact.md](answers/06-compact.md)，别偷看）。

## 🎯 本课练习目标

- 能解释"真实计数优先 + 条数兜底"的双触发
- 能说清为什么摘要放独立字段而不是消息列表
- 能读懂压缩提示词"保留什么、省略什么"

---

## ✍️ 练习

### 练习 1：读代码——contextUsage（入门）

**目标**：理解"不要傻傻把每条消息的 token 加起来"。

**步骤**：

1. 读 `contextUsage`（约 L18-46）。
2. 回答：它以什么为"基准"来估算占用？为什么这样比"累加每条消息"准？
3. 追问：如果一条消息没有 token 记录（早期数据），估算函数 `estimateTokens` 是怎么补的？

**预期结果（自检）**：能说出"以最近一次带真实 input count 的 assistant 消息为基准（API 已含全部历史），再对之后新增的消息做估算"；中文约 0.7 token/字、其他约 0.25 token/字符。

**提示**：API 每次返回的 `input_tokens` 是"这次送进去的完整输入"——不是这一条消息的增量。

---

### 练习 2：读代码——双触发（入门）

**目标**：说清"百分比阈值 + 条数兜底"为什么缺一不可。

**步骤**：

1. 读 `shouldCompact`（约 L101-106）。
2. 回答：什么时候走"条数兜底"？什么时候走"token 占用"？
3. 构造一个场景，让"条数兜底"在"token 占用"失效时兜住。

**预期结果（自检）**：能说出"消息 > 40 条就压（保守兜底）／占用 > 窗口 90% 就压（精确主方案）"；并构造出"每条消息都很短、没到 90%，但条数很多"的场景。

**提示**：`COMPACT_MIN_MESSAGES=40` 是条数，`COMPACT_PCT=90` 是百分比。

---

### 练习 3：动手——快速触发压缩（进阶）

**目标**：亲眼看到压缩发生。

**步骤**：

1. 启动时设 `NOVA_AGENT_COMPACT_MIN=5`。
2. 聊 6 条左右，触发压缩。
3. 看前端横幅"已压缩 N 条" + 对话区顶部摘要；再读 `session.summary` 字段，对照"保留目标/完成/待办、省略寒暄"的要求。

**预期结果（自检）**：压缩横幅出现；`session.summary` 里是浓缩摘要而不是逐字记录；旧消息从消息列表消失、摘要进 system prompt。

**提示**：摘要**不进消息列表**，放 `session.summary` 独立字段——注意看代码里哪一行做的这件事。

---

### 练习 4：为什么摘要不放进消息列表（挑战）

**目标**：理解"独立字段"的设计意图。

**步骤**：

1. 读 `compactSession`（约 L111-125）与 agentLoop 里 `summaryBlock` 的拼装。
2. 推理：如果把摘要当普通消息 push 进 `session.messages`，会发生什么？（从"再计数/再压缩"角度）
3. 说出"独立字段"的两个好处。

**预期结果（自检）**：能说出——若进消息列表：① 摘要会被下一轮压缩当成"要总结的旧消息"之一，越滚越大；② 它参与 contextUsage 计数，污染占用判断。独立字段的好处：每轮固定拼进 prompt、干净可控、不被再压缩。

**提示**：想想"摘要"本身也是文本，也有 token 成本；放哪决定了它会不会被再次压缩。
